# SPEC 02 — Levels, power-ups, skins, and high score

> **Status:** Approved
> **Depends on:** SPEC 01
> **Date:** 2026-10-30
> **Objective:** Extend the playable MVP with endless generated levels, three falling power-ups (Triple ball, Complete bar, Frenzy), hue-shifted skins (Retro, Pastel, Neon) chosen on the game over screen, and a high score saved in `localStorage`.

---

## Why this spec exists

SPEC 01 deliberately left out level progression, power-ups, multiple balls, speed changes, and high-score persistence. This spec adds them together as one quality-of-life pass.

The `/spec` review flagged that four areas in one spec is over the usual size limit and recommended splitting it into three specs. The user chose to keep it as one spec. The implementation plan is therefore ordered so that each step is commitable and runnable on its own, and the spec can still be implemented in pieces.

---

## Scope

**In:**

- **Levels:** clearing every brick advances to the next level instead of just regenerating the same wall. Layouts are generated by code, seeded by the level number, so the same level always looks the same. There is no last level.
- **Level difficulty:** ball base speed grows 5% of `BALL.speed` per level, capped at 2x.
- **High score:** one number saved in `localStorage`, shown in the HUD and on the game over screen, written at game over.
- **Power-ups:** every destroyed brick has a 10% chance to drop a capsule that falls and must be caught by the paddle. The three types are Triple ball, Complete bar, and Frenzy.
- **Multiple balls:** `state.ball` becomes `state.balls`. A life is lost only when the last ball on screen falls.
- **Skins:** Retro (default, unmodified sprites), Pastel, and Neon, made by applying a canvas filter (hue shift plus saturation/brightness) to the spritesheet.
- **Skin menu:** on the `gameover` screen only, Left/Right arrows pick the skin and Space or click starts the new game.
- **HUD:** adds level number, high score, and the remaining seconds of active timed power-ups.
- Updating `CLAUDE.md` (project status, new constants and state).

**Out of scope (for future specs):**

- Hand-made or editor-made level layouts.
- Armored (gray) multi-hit bricks and other brick types.
- More power-ups than the three listed (lasers, sticky paddle, extra life, wider paddle).
- Sounds for capsule drop, catch, or power-up expiry (existing `ball-bounce.mp3` and `break-sound.mp3` only).
- Skin choice persistence (it resets to Retro on every page load).
- Changing the background color, HUD text color, or capsule colors per skin. Only the spritesheet is filtered.
- A high-score table with names or dates. Only a single number is stored.
- Win screen, pause, title screen, or menus other than the game over skin picker.
- Touch/mobile controls.
- Automated tests, build system, or package manifest.

## Data model

```js
// New constants (game.js)
const LEVEL = {
  speedStep: 0.05,        // +5% of BALL.speed per level above 1
  speedCapFactor: 2,      // base speed never exceeds BALL.speed * 2 (640 px/s)
  holeChanceStep: 0.1,    // hole probability = min(holeChanceMax, (level - 1) * step)
  holeChanceMax: 0.5,
};
const POWERUP = {
  dropChance: 0.10,       // per destroyed brick; mutable on purpose, to force drops from the console
  types: ['triple', 'bar', 'frenzy'],   // each equally likely once a drop happens
  capsule: { w: 32, h: 16, fallSpeed: 120 },   // px, px/s
  barDuration: 10,        // seconds
  frenzyDuration: 10,     // seconds
  frenzyFactor: 2,        // ball speed multiplier
  tripleAngle: 25 * Math.PI / 180,   // rotation of the two new balls
  maxBalls: 6,
};
const BAR = { y: 468, h: 8 };   // full-width bar under the paddle (paddle is at y 440, h 12)
const MAX_STEP = 8;             // px; max distance a ball moves per collision sub-step

const SKINS = {
  retro:  { label: 'Retro',  filter: 'none' },
  pastel: { label: 'Pastel', filter: 'hue-rotate(20deg) saturate(0.55) brightness(1.25)' },
  neon:   { label: 'Neon',   filter: 'hue-rotate(-30deg) saturate(2.2) contrast(1.2) brightness(1.1)' },
};
const SKIN_ORDER = ['retro', 'pastel', 'neon'];

const STORAGE = {
  highScore: 'arkanoid:v1:highscore',   // stored as a decimal integer string
};

// State changes (game.js)
const state = {
  // ...fields from SPEC 01, except `ball`, which is replaced by `balls`
  level: 1,
  highScore: 0,                       // loaded from localStorage at startup
  newRecord: false,                   // true when the finished game beat the stored high score
  balls: [/* { x, y, vx, vy } */],    // same shape as the old `ball`; 1 ball in `ready`
  capsules: [/* { x, y, type } */],   // x, y = top-left of the capsule
  effects: {
    bar: 0,                           // remaining seconds, 0 = inactive
    frenzy: 0,                        // remaining seconds, 0 = inactive
  },
  skin: 'retro',                      // key of SKINS
};
```

```js
// New helpers (names fixed so the plan and criteria can reference them)
// game.js
//   generateLevel(level)  -> array of 6 rows x 10 booleans (true = brick), pure and seeded
//   baseBallSpeed(level)  -> px/s, includes the cap, excludes Frenzy
//   currentBallSpeed()    -> baseBallSpeed(state.level) * (frenzy active ? POWERUP.frenzyFactor : 1)
//   loadHighScore() / saveHighScore(n)  -> localStorage access wrapped in try/catch
// assets/spritesheet.js
//   applySkin(filter)     -> rebuilds the drawing source from the original sheet using ctx.filter
```

Conventions:

- `generateLevel` uses a small seeded PRNG (mulberry32) seeded with the level number. It generates the left 5 columns and mirrors them to the right 5, so layouts are left-right symmetric. Each cell is a hole with probability `min(holeChanceMax, (level - 1) * holeChanceStep)`. Level 1 therefore has no holes and matches the SPEC 01 wall. If a generated layout has no brick at all, the first cell is set to a brick.
- Brick colors still follow `ROW_COLORS` by row.
- Base speed is `BALL.speed * min(speedCapFactor, 1 + speedStep * (level - 1))`, which reaches the 2x cap at level 21. Frenzy multiplies the current base speed by 2 and is not subject to the cap.
- Every ball keeps `currentBallSpeed()` after each bounce (renormalization from SPEC 01 now uses this function instead of `BALL.speed`).
- Ball movement is split into sub-steps of at most `MAX_STEP` px, with collisions resolved after each sub-step. At the maximum speed (1280 px/s, level 21+ with Frenzy) and `dt` = 1/30 s, a frame moves about 43 px, so it takes 6 sub-steps.
- Time-based effects count down with `dt` only while `mode === 'playing'`.

## Implementation plan

1. **Balls array and sub-stepping.** Replace `state.ball` with `state.balls` (one ball), update every reference (movement, drawing, launch, lives), and move the ball in sub-steps of at most `MAX_STEP` px. Lose a life only when `state.balls` is empty. Add `currentBallSpeed()` returning `BALL.speed` for now. Manual test: the game plays exactly as in SPEC 01 (bounces, bricks, lives, game over).
2. **Levels.** Add `state.level`, `generateLevel`, `baseBallSpeed`, and `LEVEL`. Build the wall from `generateLevel(state.level)`. Clearing the last brick increments the level, rebuilds the wall, returns to `ready`, and keeps score and lives. A new game after game over resets the level to 1. Add the level number to the HUD. Manual test: from the console, destroy all bricks but one, break the last one, and see "Level 2" with a wall that has holes and a ball slightly faster than 320 px/s; reloading and reaching level 2 again gives the same layout.
3. **High score.** Add `STORAGE`, `loadHighScore`, `saveHighScore`, `state.highScore`, and `state.newRecord`. At game over, if `score > highScore`, save it and set `newRecord`. Show `HI` in the HUD (the larger of the saved value and the current score) and the high score plus a "New record" line on the game over screen. If `localStorage` throws, keep the value in memory only. Manual test: finish a game with score above 0, reload the page, see the same `HI`.
4. **Capsule drops.** Add `POWERUP`, `state.capsules`, and the drop roll when a brick is destroyed (`Math.random() < POWERUP.dropChance`, type chosen uniformly). Capsules fall at `fallSpeed`, are drawn as a rounded rectangle with the letter T, B, or F, are removed when they leave the canvas, and are removed with no effect when they overlap the paddle (the effect is wired in the next steps). Capsules are cleared on life loss, level change, and game over. Manual test: set `POWERUP.dropChance = 1` in the console, break a brick, see a capsule fall and disappear when caught or missed.
5. **Triple ball.** Catching a `triple` capsule takes the first ball in `state.balls` and adds two balls at its position, with its velocity rotated by +25° and -25°. If adding would pass `maxBalls`, add only as many as fit. Draw and update every ball; each ball collides with paddle and bricks independently. Manual test: catch a T capsule and see 3 balls; let one fall and keep playing without losing a life; let all fall and lose exactly one life.
6. **Complete bar.** Catching a `bar` capsule sets `effects.bar = POWERUP.barDuration` (refreshing if already active). While `effects.bar > 0`, draw a full-width bar at `BAR.y` and bounce balls off its top, playing `ball-bounce.mp3`. The effect counts down with `dt` while playing and ends at 0. Manual test: catch a B capsule, see the bar for 10 s, see balls bounce on it, see it disappear.
7. **Frenzy.** Catching a `frenzy` capsule sets `effects.frenzy = POWERUP.frenzyDuration` (refreshing if already active) and rescales every ball velocity to `currentBallSpeed()`. When it expires, every ball is rescaled back. Show active effect timers in the HUD. Manual test: catch an F capsule, see the ball move twice as fast for 10 s, then return to normal speed; no ball tunnels through bricks or the paddle.
8. **Effect cleanup.** Reset `effects` and `capsules` on life loss, level change, and game over, and confirm Frenzy ball speed is undone with them. Manual test: catch Frenzy and the bar, then lose the last ball; after relaunch there is no bar, normal speed, no capsules.
9. **Skin engine.** In `assets/spritesheet.js`, keep the original sheet canvas and add `applySkin(filter)`, which draws it onto a new offscreen canvas with `ctx.filter = filter` and makes `drawSprite` / `drawFrame` use that canvas. Do nothing if `ctx.filter` is unsupported. Add `SKINS`, `SKIN_ORDER`, and `state.skin`. Manual test: in the console, call `applySkin(SKINS.neon.filter)` and see the bricks, paddle, ball, and explosions change color; `applySkin('none')` restores them.
10. **Skin menu.** On the `gameover` screen, list Retro / Pastel / Neon with the current skin highlighted. Left/Right arrows (or A/D) change `state.skin` and call `applySkin` immediately. Space or click starts the new game with that skin. Manual test: lose the game, press Right to see the colors change, press Space and play with the chosen skin; reload and see Retro.
11. **Docs.** Update `CLAUDE.md` (project status, new constants and state, the `applySkin` helper, and the removal of the "Out of scope" items from SPEC 01 that this spec covers). Manual test: `CLAUDE.md` describes the real project.

## Acceptance criteria

- [ ] The game loads with no console errors and starts on level 1 with the full 6x10 wall and the Retro skin.
- [ ] The HUD shows score, high score (`HI`), level, and lives.
- [ ] Clearing every brick moves to level 2: the level number increases by 1, the game returns to `ready`, and score and lives are unchanged.
- [ ] Level 2 has at least one missing cell in the 6x10 grid and is left-right symmetric; reloading the page and reaching level 2 again gives the identical layout.
- [ ] `generateLevel(1)` returns 60 bricks, and `generateLevel(n)` returns the same result every time for the same `n`.
- [ ] The ball speed at level 2 is 336 px/s, at level 11 is 480 px/s, and at level 21 and above is 640 px/s.
- [ ] Starting a new game after game over resets level to 1, score to 0, and lives to 3.
- [ ] After a game over with a score above the stored high score, reloading the page shows that score as `HI`.
- [ ] Reaching a lower score than the stored high score does not change the stored value.
- [ ] The game over screen shows the high score, and shows a "New record" line only when the finished game beat the previous high score.
- [ ] With `localStorage` unavailable (access throws), the game still runs and `HI` works in memory for the current session.
- [ ] With `POWERUP.dropChance = 1`, every destroyed brick spawns a capsule that falls at 120 px/s; with `POWERUP.dropChance = 0`, none spawn.
- [ ] Over 1000 brick breaks with the default `dropChance`, the number of drops is between 70 and 130 (about 10%).
- [ ] An uncaught capsule leaves the canvas and is removed; a capsule that overlaps the paddle is removed and applies its effect.
- [ ] Catching Triple ball while one ball is on screen results in 3 balls, with the two new balls moving 25° to each side of the original direction at the same speed.
- [ ] The total number of balls never exceeds 6.
- [ ] Losing one of several balls does not cost a life; losing the last ball costs exactly one life.
- [ ] While Complete bar is active, a full-width bar is drawn under the paddle, balls bounce on it, and it disappears after 10 seconds of `playing` time.
- [ ] Catching Complete bar or Frenzy again while active resets its timer to 10 seconds.
- [ ] While Frenzy is active, every ball moves at twice `baseBallSpeed(level)`; after 10 seconds every ball is back to `baseBallSpeed(level)`.
- [ ] No ball passes through a brick, the paddle, or the bar at Frenzy speed on level 21+ (1280 px/s) over a 60-second run.
- [ ] The bar, Frenzy, and falling capsules are all cleared on life loss, level change, and game over.
- [ ] The HUD shows the remaining seconds of the bar and Frenzy while each is active.
- [ ] Retro draws the original sprites; Pastel and Neon draw visibly different colors for the paddle, ball, bricks, and explosions.
- [ ] The skin menu is shown only on the game over screen; Left/Right change the skin immediately, and Space or click starts a new game with the chosen skin.
- [ ] Reloading the page always starts with the Retro skin.
- [ ] Capsules, background, and HUD text look the same in all skins.
- [ ] `ball-bounce.mp3` plays on a bar bounce.
- [ ] The only new files in the project are this spec (`specs/02-levels-powerups-skins-highscore.md`); `index.html`, `game.js`, `assets/spritesheet.js`, and `CLAUDE.md` are modified.

## Decisions

- **Yes:** a single spec for all four features. The user chose it over the recommended split into three specs; the implementation plan is ordered so each step stays commitable on its own.
- **Yes:** generated levels, seeded by the level number. The same level is reproducible for testing and the game has no last level.
- **No:** fresh random layouts each run (cannot be reproduced when debugging), hand-made layouts (the user wanted generated ones), and a fixed set of formulas (less variety).
- **Yes:** left-right symmetric layouts with holes. Random holes alone look messy; symmetry keeps the wall readable with a tiny generator.
- **Yes:** level 1 has no holes, because the hole chance starts at 0. It matches the SPEC 01 wall.
- **Yes:** +5% ball speed per level, linear, capped at 2x base. The user chose this over a flat speed. This replaces the SPEC 01 decision "no speed increase over time" only for level changes; speed does not change within a level except through Frenzy.
- **Yes:** the cap is 640 px/s. Collisions are made safe by sub-stepping rather than by a lower cap.
- **No:** a 1.5x cap and no cap. The first was safer but flatter; the second eventually tunnels.
- **Yes:** collision sub-steps of at most 8 px. Frenzy at the cap reaches 1280 px/s, about 43 px per frame, which would tunnel through 12 px of paddle or 16 px of bar without sub-stepping.
- **Yes:** power-ups are falling capsules that the paddle must catch. It adds skill and is the classic behavior; instant effects were discarded as too trivial.
- **Yes:** 10% drop chance per destroyed brick, equal chance for each of the three types.
- **Yes:** Triple ball splits only the first ball into 3 and caps the total at 6 balls. Tripling every ball was discarded because the count would grow quickly and hurt performance and readability.
- **Yes:** Complete bar and Frenzy last 10 seconds and refresh to 10 seconds when caught again. A Frenzy that lasts until the ball falls and a no-refresh rule were discarded.
- **Yes:** timers run only in `playing` mode. Waiting in `ready` does not burn them.
- **Yes:** power-up effects and capsules clear on life loss, level change, and game over. A fresh serve should always start with normal rules.
- **Yes:** the high score is saved only at game over, as one integer under `arkanoid:v1:highscore`. The versioned key allows a migration later. Closing the tab mid-game loses that session's score; accepted for simplicity.
- **No:** saving on every point and a high-score table.
- **Yes:** the HUD `HI` shows the larger of the saved value and the current score, so the player sees the record move live without extra writes.
- **Yes:** skins use `ctx.filter` (hue shift plus saturation/brightness/contrast) on an offscreen copy of the sheet. It needs no new art and Retro stays the untouched original. A hue-only shift was discarded because Pastel and Neon would differ only in color angle, not in tone.
- **Yes:** the skin is picked on the game over screen only, and it is not saved. The user chose this over a key that cycles skins at any time. Resetting to Retro on reload is accepted.
- **Yes:** capsules, background, and HUD text ignore the skin. Only the spritesheet is filtered.
- **No:** new sounds for power-ups. They can be added in a later spec once assets exist.

## Risks

| Risk                                                                      | Mitigation                                                                                            |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Tunneling at Frenzy speed on high levels (up to 1280 px/s)                | Sub-steps of at most `MAX_STEP` = 8 px per collision check; acceptance criterion covers a 60-second run. |
| `ctx.filter` is not supported in some browsers (older Safari)              | `applySkin` does nothing when unsupported, so the game stays on Retro and is fully playable.          |
| `localStorage` blocked or full (private mode, disabled storage)            | `loadHighScore` / `saveHighScore` use try/catch and fall back to the in-memory value.                 |
| Invalid or tampered stored value                                          | Parse as an integer; if not a finite number ≥ 0, treat it as 0.                                       |
| Several balls collide with the same brick in one frame                    | Each brick has `alive`; the first ball that hits it destroys it, and the others skip it that frame.   |
| Balls share one velocity renormalization, and Frenzy changes the target speed | `currentBallSpeed()` is the single source for speed; Frenzy start and end rescale all balls from it. |
| `game.js` keeps growing in a single file                                  | Still acceptable for now; splitting into modules is a decision for a later spec.                      |
| Hue-rotated sheets may look wrong for some sprite colors                   | The filter values live in `SKINS` and can be tuned without changing code structure.                   |

---

## What is **not** in this spec

- Hand-made level layouts or a level editor.
- Armored (gray) bricks or any new brick type.
- Power-ups other than Triple ball, Complete bar, and Frenzy.
- Sounds for power-ups.
- Saving the chosen skin between sessions.
- Per-skin backgrounds, HUD colors, or capsule colors.
- A high-score table, names, or dates.
- A win screen, pause, title screen, or any menu besides the game over skin picker.
- Touch or mobile controls.
- Automated tests, build tools, or a package manifest.

Each one of those, if it lands, goes in its own spec.
